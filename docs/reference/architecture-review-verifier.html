A scan of the verifier core for deepening opportunities — turning shallow modules, whose interface costs nearly as much as their implementation, into deep ones. Each candidate is put through the deletion test: would removing it concentrate complexity, or just move it around? Only a "concentrates" is worth doing.

1 · The Candidate.runs primitive obsession

verifier.py · Candidate, _experiment · every caller of run_and_record
Strong
Problem

The verifier's front door takes runs: Sequence[dict[str, Any]] — a bag of loosely-typed dicts that _experiment reconstructs into RunResult deep inside the module. The seam accepts anything shaped vaguely like a run; a malformed dict fails with a raw TypeError during gate evaluation, far from where the bad value entered. The interface is wide (accepts all dicts) but the module is shallow — it immediately does validation work the type system should have done at the boundary.

Solution

Make RunResult the currency of the seam. Candidate.runs becomes Sequence[RunResult]; construction validates once, at the edge. The _experiment bridge — which exists only to translate dicts into the real type — largely dissolves.

before · shallow
Candidate.runs : Sequence[dict]
↓ dict flows inward, untyped
_experiment(): RunResult(**r) ← fails here, late
gate sees malformed data
after · deep
Candidate.runs : Sequence[RunResult]
↓ validated at the door
_experiment(): trivial pass-through
gate always sees valid data
Deletion testRemoving _experiment after this change concentrates — the dict→type translation stops being a hidden step and becomes the constructor's job. A yes.

2 · Duplicated VerdictBundle construction

verifier.py · GateVerifier.run, ExitCodeVerifier.run (4 construction sites)
Strong
Problem

Both verifiers hand-assemble a VerdictBundle field by field, and the "two implementations, one bundle shape" contract lives only in the fact that the two call sites happen to agree. Add a field to the bundle and you edit both — classic shotgun surgery. The bundle's own construction logic has no locality: it's smeared across the two things that produce it.

Solution

Give VerdictBundle two named constructors — from_experiment(exp) and from_exit_code(candidate, proc). The shape is defined once, on the type that owns it. Each verifier calls one line. The contract becomes enforced by the type rather than by two call sites agreeing.

before · shallow
GateVerifier.run → VerdictBundle(exp_id=…, promoted=…, blocked_by=…, ×10 fields)
ExitCodeVerifier.run → VerdictBundle(exp_id=…, promoted=…, ×10 fields)
shape agreement is implicit
after · deep
VerdictBundle.from_experiment(exp)
VerdictBundle.from_exit_code(cand, proc)
shape owned in one place
Deletion testThe two constructors concentrate the bundle's shape onto the bundle. Deleting the inline construction removes duplication rather than relocating it. A yes.

3 · with_exp_id — speculative generality

verifier.py · VerdictBundle.with_exp_id · only caller is a test helper
Strong
Problem

A production method that exists solely to let a test stamp a deterministic id for ledger-ordering assertions. The test is driving production API in the wrong direction — the seam grew a method to serve the test rather than the test observing the seam. Flagged by both axes of the earlier code review.

Solution

Delete it. Let the test control the id through the actual seam — inject a deterministic id source into the verifier, or assert on ledger order via the fields the bundle already exposes. The production surface shrinks; the test still gets what it needs, honestly.

Deletion testPure win: deleting with_exp_id concentrates nothing and moves nothing — the responsibility was never real. This is the textbook "inline it back until a real need shows."

4 · The Experiment ↔ VerdictBundle entanglement

verifier.py + harness.py · GateVerifier reaches through Experiment internals
Worth exploring
Problem

GateVerifier.run reaches into Experiment — exp.blocked_by, exp.mean_metric, r.seed for r in exp.runs, g.name for g in exp.gates — to build the bundle. That's feature envy: the verifier wants data that lives on Experiment. The two types were split when verifier.py was carved from the prototype's harness.py, and the seam between them still leaks.

Why only "worth exploring"

Deepening here means deciding whether Experiment and VerdictBundle should be one type or stay two with a clean .to_verdict() method. That's a genuine design fork, not a mechanical move — and candidate 2 (named constructors) may resolve most of the envy on its own. Worth a look after 2, to see how much friction remains.

Top recommendation

Do 3, then 1, then 2 — and let 4 decide itself

Candidate 3 first (with_exp_id): it's a pure deletion with no design decision attached, and it removes a test-driven wart before the other refactors touch the same type. Cheapest possible win, and it de-risks the rest by shrinking the surface.

Then candidate 1 (typed runs): the highest-leverage of the four. It moves validation to the seam, dissolves the _experiment bridge, and fixes the error-locality problem the code review flagged — a malformed run now fails at the door with a clear message instead of deep in gate evaluation.

Then candidate 2 (named constructors): mechanical once 1 has settled the field types, and it kills the shotgun-surgery risk before the runner (ticket 07) adds a third bundle producer.

Candidate 4 last, maybe never: re-scan the envy after 2. If the named constructors already localise the crossing, 4 dissolves for free — which is the best outcome. Only open the Experiment/VerdictBundle merge question if real friction survives.

One cautionAll 34 tests are green and test at real seams. The refactor's job is to keep every one of them green while shrinking the surface — if a test has to change, that test was coupled to an implementation detail, and the change is telling you something.
