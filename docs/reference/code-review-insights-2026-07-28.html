Independent code and web review · 28 July 2026 · repository HEAD 0e67b0c

expfactory is on the right track — but its live boundary is not ready yet.

The project has an unusually sound thesis: do not ask the producer of an empirical result to certify it. Its trust boundaries, negative acceptance criterion, and decision record are real strengths. The next work should be narrower and more urgent than expanding gates: make every promoted number and every budget event originate from trusted, durable infrastructure.

Bottom line. Keep the architecture. Do not dispatch a real empirical agent yet. First close the four P0/P1 paths below: finite-value validation, trusted cost accounting, durable/idempotent job submission, and end-to-end attestation binding. These are not cosmetic hardening; each currently lets an untrusted party bypass a stated control or leaves an expensive run unaccounted for.

What is already notably good

  • The central boundary is correct. AgentSession returns a Candidate; Runner owns a verifier and adjudicates it. That removes the easy failure mode of the producer returning a pre-approved verdict.
  • The project treats rejection as success when appropriate. This is exactly the mindset an empirical factory needs and prevents benchmark-chasing from becoming a hidden acceptance criterion.
  • Gates have fixtures and a held-out discipline. The visible/held-out adversarial split and the policy not to tune against the held-out partition are disciplined, evidence-oriented choices.
  • Trust design is concrete. Human-applied dispatch labels, separate runner credentials, workspace-name refusal, a non-overridable L0, and an explicit review-cap back-pressure mechanism are much stronger than relying on prompts or role names.
  • The project is honest about incomplete work. DISPATCH-READINESS.md and NEXT.md name several gaps rather than claiming the system is deployed. Preserve that standard.

Findings

P0 — block live dispatchIntegrity

1. Non-finite metrics can turn an impossible result into a promotion

Candidate/RunResult accepts arbitrary floats without requiring finiteness. With three clean runs whose val_metric is float("inf"), the base GateVerifier promotes the candidate. The dominance arithmetic becomes nan, whose comparisons are false, and the other gates do not reject it. The reproduction during this review returned promoted=True and mean_metric=inf.

This is a direct violation of “evidence, not verdict”: a malicious or faulty producer can send an infinity rather than a real result. The preregistration path may reject some such cases, but numeric validity must not depend on an optional or workflow-specific gate.

Fix: validate all numerical boundary fields once, at candidate/run construction: finite metric values, finite non-negative duration and cost, integer non-negative overlap, and finite preregistration/guardrail parameters. Add adversarial fixtures for NaN, +/-inf, negative cost, and duplicate seeds where required. Fail the candidate loudly rather than converting it.

Evidence: src/expfactory/verifier.py:66-107, src/expfactory/harness.py:204-237, src/expfactory/gates_v1.py:225-252. Reproduced locally in this review.

P0 — block live dispatchCost control

2. The registry accepts negative and NaN job-cost estimates

JobRegistry.submit() tests only whether an estimate is greater than a cap. Therefore -100.0 and NaN both pass the per-job and per-day checks and are recorded. The review reproduced both accepted submissions. A negative value also lowers the trailing-day total, creating additional apparent budget.

More fundamentally, a caller-provided estimate is not a cap if the untrusted caller can choose it. The registry must derive or verify the maximum charge from trusted job parameters and provider pricing before submission; actual provider-reported usage should be reconciled afterwards.

Fix: reject every non-finite or negative input and invalid cap/deadline at construction. Replace the free cost_estimate_usd argument at the untrusted request boundary with a trusted admission/pricing function keyed by image, GPU SKU, requested duration, and provider rate card. Reserve the worst-case amount before submit, reconcile actual spend, and retain the reservation on uncertainty.

Evidence: src/expfactory/registry.py:317-372. Reproduced locally in this review.

P1 — fix before detached GPU runsDurability

3. Submission has an unrecoverable crash window and no multi-writer guarantee

The registry calls the substrate first and appends its submitted event afterwards. A process failure in that gap creates a live, billable job with no registry record. The documented reconcile() cannot find it because it only polls records already in the log. Separately, cap-check → submit → append is not locked or transactional, so two runner processes can both admit work against the same daily budget.

Fix: make submission an explicit state machine: durable intent/reservation with an idempotency key → provider submission carrying that key → durable handle binding. On startup, reconcile both reservations and provider-side jobs by key, not only known handles. Use a single-writer service/database transaction or an OS/database lock around the admission/reservation transition. Make log writes durable enough for the stated recovery model (flush/fsync or a transactional store).

Evidence: src/expfactory/registry.py:187-224, 317-373, 442-453; docs/SPEC.md specifies a single-writer assumption only for the verdict ledger, not this compute ledger.

P1 — fix before using G-10 as evidenceAttestation

4. G-10 currently proves only that a handle exists, not the claimed artifact or ticket

RunAttestation models command, exit code, wall time, and artifact digest, and the gate knows how to compare digest/exit code and ticket. But the real registry stores none of those completion values in attested_job(); it returns only handle, ticket, state, submission time, and artifact reference. The verifier also passes no ticket to the gate. Consequently, a candidate can cite a registry-issued handle with arbitrary artifact digest/exit code, and a handle from another ticket is not bound in the production verifier. The tests explicitly document the latter as currently slipping through.

Fix: have the substrate/control plane write a signed or control-plane-authenticated completion record containing the ticket/job id, immutable source revision, command/image digest, exit status, timestamps, artifact digest, and evaluator-output digest. Store and verify it before parsing a candidate. Bind the runner’s ticket id to verification, or make the attestation-to-ticket mapping an immutable lookup performed by the runner. Treat the candidate as a request to locate trusted output, not as the source of the attestation.

Evidence: src/expfactory/registry.py:85-115, 259-279; src/expfactory/verifier.py:405-416; src/expfactory/gates_v1.py:437-459; tests/test_attested_run.py:159-173.

P2 — reliability / readinessIntegration

5. The detach path cannot reach “Running Unattended” through either production tracker

Runner._detach() only requires a collector, not a job ledger, so it can park a ticket that no component will poll. It then asks the tracker to set Running Unattended; neither the GitHub label mapping nor the Linear writable-state allowlist supports that state. A fake tracker makes unit tests pass, but the production adapters reject it. Both adapters also fetch only their first page of issues/history, which can indefinitely skip old tickets or fail closed after normal queue growth.

Fix: refuse detachment unless both registry and collector are configured; add the unattended state to the supported tracker state model with adapter integration tests; and implement cursor/link pagination with an explicit ordering policy. Treat an impossible tracker transition as a pre-dispatch configuration error, not a post-submit exception.

Evidence: src/expfactory/runner.py:552-577; src/expfactory/github_tracker.py:31-37; src/expfactory/linear_tracker.py:35-37.

Recommended sequence

  1. Make the numerical and cost boundaries total. Add a shared finite/non-negative validator and adversarial cases first; it is cheap and closes direct bypasses.
  2. Redesign compute admission as a durable reservation protocol. This is the foundation for honest caps and restart recovery; do not build a Modal adapter on the current submit-then-record shape.
  3. Replace candidate-authored attestations with trusted completion provenance. Bind job ↔ ticket ↔ source/image ↔ artifact ↔ evaluation result. The trusted scorer should read the immutable artifact and emit the metric, rather than trusting a metric inside agent-written output.
  4. Wire the full detached path against real adapters. Exercise submit, restart, collection, timeout, cancellation, and a tracker outage end to end with a short deterministic workload before training anything.
  5. Only then add breadth. More gates, MLflow, and L1 review are valuable later, but none compensate for a result or budget that originates in the untrusted side.

Landscape expansion: software factories and agent factories

This follow-up reviewed the current official sites and public repositories for the systems below. The useful question is not “which system has the most agents?” It is: which control is enforced outside the agent that benefits from bypassing it? That is the boundary expfactory is trying to make real.

Important correction to the earlier landscape note. GitHub Agentic Workflows (gh-aw) now documents hard AI-credit limits per run and per workflow per day, plus a separate safe-output stage. So “no upstream cost enforcement” is too broad for agent inference. It remains true that this does not price, reserve, or cap long-lived GPU experiment work, and it does not adjudicate the truth of an empirical metric.

The three patterns that materially improve expfactory

  1. Adapt gh-aw’s safe-output split to evidence. The agent should request a job or name an artifact; a separate runner-owned component should obtain provider completion metadata, invoke the trusted scorer, and produce the candidate/verdict inputs. This is the clearest available implementation pattern for your invariant that the untrusted party returns evidence rather than a verdict.
  2. Adopt a two-level budget design. Delegate LLM-token caps to the provider/runtime that holds the model credential (as gh-aw does for AI credits); retain expfactory-owned GPU reservation, daily cap, and breaker because no coding-agent framework can truthfully price your compute substrate for you.
  3. Add a context-evaluation lane, not more prose. Tessl’s lifecycle reinforces your ratchet: treat skills and AGENTS.md as versioned inputs with scenario evaluations. Track whether they improve task behavior, while keeping policy enforcement in deterministic gates, CI, or post-processing jobs.

None of these changes overturn the thesis. They sharpen the division of labor: adopt mature agent harness/security machinery; build the empirical ledger, trusted scorer, evidence provenance, and compute controls that those systems intentionally do not provide.

Conclusion

The differentiator is real: the project is not another agent runner that treats a green-looking number as success. Its core decision — verification must be outside the producer’s reach — is exactly right. The remaining risk is implementation completeness at that same boundary. Concentrate the next milestone on a trusted control plane that produces the metric provenance and reserves cost before work starts. Once that is true, the gates and the carefully designed human process will have a reliable foundation to stand on.
